# Development

*Part of the [siann documentation](README.md#documentation).*

[IMPLEMENTATION](IMPLEMENTATION.md#code-layout) describes how the code is organized; [What does not pay](#what-does-not-pay),
at the end, lists the ideas measured and dropped.

## Setup

You need [Rust](https://rustup.rs) and [uv](https://docs.astral.sh/uv/getting-started/installation/).
Then:

```sh
git clone https://github.com/vglazer/siann
cd siann
uv sync --group dev             # build the package, Rust extension included, with the test dependencies
uv sync --group bench           # or with the benchmarks' dependencies too (FAISS, PyTorch, mlxvs, h5py)
```

uv rebuilds the Rust extension (`siann._cpu`, compiled by maturin, the tool that packages Rust code as a
Python module) whenever its sources change.

## Tests and linting

```sh
uv run python -X warn_default_encoding -m pytest -W error::EncodingWarning   # Python tests
uv run --only-group lint ruff check .                                          # lint the Python code
cd crates/siann-py && cargo fmt --check && cargo clippy --release -- -D warnings   # the Rust code
```

CI runs the tests and the Rust checks on Linux, macOS and Windows, and ruff on Linux. The GPU backend runs
only on Apple silicon and GitHub's Mac runners may lack a usable GPU, so the GPU tests skip in CI; run them
locally on a Mac before each release. The encoding flags make any text read or written
without a named encoding an error, so always pass `encoding="utf-8"`.

After any change to a kernel, also run every kernel and index against NumPy's exact search:

```sh
cd benchmarks && uv run --group bench python check_kernels.py
```

## Scripts

```sh
uv run --group dev python examples/make_quickstart.py   # rebuild and run the quickstart notebook
uv run --group dev python examples/make_figures.py      # redraw the README's figures
```

The quickstart notebook is generated by `examples/make_quickstart.py`: edit the script and rerun it rather
than editing the notebook; a test fails if they differ. The scripts behind [BENCHMARKS](BENCHMARKS.md) are
in `benchmarks/`, run from there with `uv run --group bench python <script>`; its
[README](benchmarks/README.md) groups them by purpose.

## Releases

The version is set in one place, `crates/siann-py/Cargo.toml`, which maturin also uses for the Python
package. Before a release, run the tests and `check_kernels.py` on a Mac with Apple silicon, where the GPU
tests run. Then commit the new version, push, and create a release on GitHub whose tag is `v` followed by
the version (for example `v0.1.0`). The release workflow (`.github/workflows/release.yml`) checks that the
tag matches the version, runs CI, builds a wheel (a built package, so that users need no Rust compiler)
for each platform:

| Platform | Wheel |
| --- | --- |
| Linux, x86-64 and ARM | manylinux: glibc-based distributions (most; not Alpine); x86-64 needs AVX2 |
| macOS, Apple silicon | macOS 11 or later; installs MLX, the GPU backend |
| Windows, x86-64 | needs AVX2 |

The x86-64 wheels are compiled for x86-64-v3, which requires AVX2 and FMA (Intel processors from Haswell,
2013, and AMD's from Excavator, 2015): that makes L1 and L-infinity search 1.5-2.4x faster than a build for
any x86-64 processor (BENCHMARKS, [On Linux](BENCHMARKS.md#on-linux)). On an older processor, `import
siann` raises an ImportError saying so (`siann._build`, checked before the Rust extension loads), and
`pip install --no-binary siann siann` builds siann for that machine from the source distribution.

and a source distribution, and smoke-tests each (`scripts/smoke_test.py`: exact search by every metric
against NumPy, an IVF reaching its recall target, a save and load) on its own platform on Python 3.12
and 3.14. The wheels are abi3, built against Python's stable interface, so one wheel per platform serves
every Python from 3.12 on. The workflow then publishes to PyPI through trusted publishing: PyPI accepts
packages from this workflow without a stored token.

To rehearse, run the workflow by hand (Actions, Release, Run workflow): it does the same, but publishes to
TestPyPI, with the version `VERSION.devN`, N the run number, since an index accepts each version only once.

## Rules for changing the code

**Results.**

- **Exact search is the oracle.** Every kernel and index is checked against NumPy's exact search
  (`check_kernels.py`). A change that should not move results is checked bit for bit against outputs
  saved before the change, on fixed seeds; a change that does move them says why.
- **A new default must be no slower than the old one on any measured case,** single queries, batches of
  100 and batches of 10,000 alike.
- **Every number in the docs comes from a committed script,** with its raw output in
  `benchmarks/results/` and its place in [BENCHMARKS](BENCHMARKS.md). An idea that does not pay goes into
  [What does not pay](#what-does-not-pay), with its numbers.

**Timing.**

- **Time each path by itself, warmed up.** A GPU call right after CPU calls runs up to 40% slower, and a
  fresh index's first GPU calls are slower than later ones, so timings taken in alternation, or cold,
  favor the CPU.

**GPU kernels.**

- **Write each kernel once,** in `siann._metal`: MLX and PyTorch compile the same text, so the two GPU
  backends cannot drift apart.
- **Keep a GPU call's working memory within `siann._memory`'s budget,** splitting the batch where it grows
  with it, and check the split returns exactly what one call does. On Apple silicon a GPU allocation past
  the machine's memory swaps or stalls the system instead of failing (`memory.py` measures each path).
- **Pass sizes such as the batch size at run time, not as compile-time constants.** Compiled in, every
  new batch size recompiles the kernel, 26-74 ms on top of a 1-4 ms search. Compile in only what sizes an
  array in registers or threadgroup memory (k, threads per query) or a loop worth unrolling (the
  dimension).

**Rust.**

- **Safe Rust only.** siann's code has no `unsafe` (code the compiler cannot check for memory safety),
  and every case so far has a safe alternative: NumPy for BLAS calls, a comparison and select for a
  maximum, a buffer for float16, plain loops over contiguous bytes for integer arithmetic. Calling
  Accelerate from Rust would be `unsafe`, so NumPy makes the call and Rust ranks the products, reading
  NumPy's arrays in place through rust-numpy (the PyO3 project's NumPy bindings).
- **Check the assembly, not just the timing.** The compiler turns plain loops into NEON instructions
  (Apple's vector instructions), and its choice of which loop to vectorize decides the speed. That choice
  is easy to see in the emitted instructions (`fabd.4s`, `udot`) and easy to miss in a timing alone.
- **Choose the layout for the arithmetic.** Floating-point sums may not be reordered, so the blocked
  layout (8 vectors per block, dimension by dimension) gives one running distance per lane. Integer sums
  may be reordered, so the integer path reads each vector's bytes contiguously.
- **Write a floating-point maximum as a comparison and select, loop over flat slices, and give one
  query's parallel work a thread pool of its own:** `f32::max`, nested arrays and rayon's global pool
  each cost speed, measured in [What does not pay](#what-does-not-pay).

## What does not pay

These are for anyone changing the code: ideas measured and dropped, so that they are not tried again
unknowingly. Each is measured; the scripts are named in parentheses, and their output is in
[benchmarks/results/](benchmarks/results/).

- **A matrix multiply in pure Rust instead of BLAS** (`faer_gemm/`, `numpy_gemm.py`). faer, the multiply in
  safe Rust, on the products exact L2 search computes: BLAS is 1.2-5.0 times faster on the Mac (Accelerate)
  and 1.1-10.4 times on Linux (OpenBLAS), most for single queries and small batches
  ([A matrix multiply in Rust](BENCHMARKS.md#a-matrix-multiply-in-rust)). Rust would avoid OpenBLAS's
  threads competing with siann's; setting `OPENBLAS_THREAD_TIMEOUT` avoids it at no such cost.

- **LSH for dense vectors** (`lsh_l1.py`). Locality-sensitive hashing hashes vectors so that near ones
  tend to collide, then compares only the colliding ones. With Cauchy random projections (the standard
  LSH for L1) on SIFT1M, reaching recall 0.72 means re-ranking a tenth of the database, which exact
  search on the GPU already does faster. Real data has low contrast: a neighbor and a point twice as
  far collide with nearly the same probability (0.28 and 0.26).
- **A fused L1 kernel** (distance and selection in one pass): it reads the whole base once per query,
  so it is limited by memory speed, at a third of the tiled kernel's speed.
- **`f32::max` for L-infinity in Rust** (`rust_cpu_sweep.py`): the compiler treats a maximum as a
  reduction it may reorder, and vectorizes the wrong loop, taking twice L1's time (an unsigned-integer
  maximum on the float bits does the same). A comparison and select keeps one running maximum per
  lane: 1.4 times L1's time.
- **Assigning an inner-product IVF's lists by inner product** (`ip_lists.py`), as FAISS's IVF does:
  the lists fall out of balance (22% empty on Music-100, 39% on raw GloVe, the largest holding 20,645
  and 35,725 vectors), and at matched recall the search is 1.7-8.4 times slower than with lists
  assigned by L2. Probing by L2 as well fails (recall at most 0.40).
- **Reducing inner product to L2** (`ip_reduction.py`): extending each vector to the same length
  balances the lists, but recall falls (below 0.82 on Music-100, 0.35 on raw GloVe), and FAISS's HNSW
  on the extended vectors does as badly: the added coordinate dominates the distances.
- **Any IVF on vectors of very uneven length** (raw GloVe, lengths 0.04 to 18.7): siann's reaches
  recall 0.443 by nprobe 128, FAISS's 0.641; use HNSW, or exact search on the GPU for recall 1.0.
- **BLAS in the CPU IVF's list-major scan** (`blas_ivf.py`): one multiply per list, its queries against
  its vectors, the products ranked in Rust. The multiplies are small (about 160 queries by 250 vectors
  at nprobe 64), so overheads dominate: 0.5-0.8 times the Rust list-major scan on batches of 10,000,
  and 0.14-0.19 times on batches of 100. With the coarse step and grouping free it would at best draw
  level. BLAS pays for exact L2, where the multiplies are large.
- **Splitting a single query on the global thread pool** (`single_query.py`): a query injected into
  rayon's pool (all 16 cores) wakes its sleeping threads, about 100 microseconds per query, slower than
  one thread at low nprobe. A pool of its own (4 threads) avoids it.
- **Widening float16 inside the distance loops in Rust**, or over nested `[u16; 8]` arrays: the
  compiler loads the halves one lane at a time. Widening each block into a buffer first, in a loop over
  flat slices, is 1.3-1.9 times faster.
- **Fewer IVF lists to cheapen the coarse step** (`coarse_step.py`): each list grows as the coarse step
  shrinks, which cancels out at matched recall.
- **A two-level coarse step in `siann.Index`** (`coarse_step.py`; `IvfIndex.set_coarse_groups` and
  `search(gprobe=)` keep it for the benchmarks): the centroids clustered into groups, a query compared with
  the groups' centres and then only with the centroids of its nearest groups (16 of 64 for 4,000 lists).
  On one thread it makes single queries 1.35-1.8 times faster on SIFT at matched recall, but the paths
  siann routes to already spread the coarse step: 1.09-1.17 times for a single query split over 4 threads,
  1.12-1.40 for batches of 8, and on GloVe 1.0-1.12 on both, least at the recall targets siann is usually
  given ([The coarse step](BENCHMARKS.md#the-coarse-step)). Each index would also need the groups built,
  saved and calibrated with.
- **Finer partitions for small batches on the CPU** (`fine_lists.py`, `batch_profile.py`): 16,000 lists
  touch 1.6 times fewer vectors than 4,000 at recall 0.97 and run at the same speed, held back by a
  fixed cost per list. On the GPU they pay at high recall.
- **An integer kernel in the blocked layout:** no faster than the float path (259 against 263
  microseconds at nprobe 64, written with the `wide` crate's vector types); the integer path needs each
  vector's bytes contiguous.
- **The integer path in the CPU's list-major scan** (large batches; `fp16_lists.py`): Rust's list-major
  scan with uint8 lists does 38,567 queries per second on SIFT at nprobe 64, against the GPU IVF's
  199,347 and compressed HNSW's 153,710; even the single-query path's gain (1.6-1.8 times) would leave
  it far behind both.
- **Reading four coordinates per load in the GPU scan** (`uchar4`, `half4`, `float4`, with identical
  results; `gpu_load4_ab.txt`): up to 6% faster on SIFT and 20-45% slower on GloVe.
- **Routing timed with the devices in alternation** (`index_routing_ab.py`): after calls on the CPU, a GPU
  call runs up to 40% slower, so timing the two in turn favors the CPU; each path is timed by itself.
