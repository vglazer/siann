# Development

*Part of the [siann documentation](README.md#documentation).*

[IMPLEMENTATION](IMPLEMENTATION.md#code-layout) describes how the code is organized.

## Setup

You need [Rust](https://rustup.rs) and [uv](https://docs.astral.sh/uv/getting-started/installation/).
Then:

```sh
git clone https://github.com/vglazer/siann
cd siann
uv sync --group dev             # build the package, Rust extension included, with the test dependencies
uv sync --group bench           # or with the benchmarks' dependencies too (FAISS, PyTorch, mlxvs, h5py)
```

uv rebuilds the Rust extension (`siann._cpu`, compiled by maturin, the tool that packages Rust code as a
Python module) whenever its sources change.

## Tests and linting

```sh
uv run python -X warn_default_encoding -m pytest -W error::EncodingWarning   # Python tests
uv run --only-group lint ruff check .                                          # lint the Python code
cd crates/siann-py && cargo fmt --check && cargo clippy --release -- -D warnings   # the Rust code
```

CI runs the tests and the Rust checks on Linux, macOS and Windows, and ruff on Linux. The GPU backend runs
only on Apple silicon and GitHub's Mac runners may lack a usable GPU, so the GPU tests skip in CI; run them
locally on a Mac before each release. The encoding flags make any text read or written
without a named encoding an error, so always pass `encoding="utf-8"`.

After any change to a kernel, also run every kernel and index against NumPy's exact search:

```sh
cd benchmarks && uv run --group bench python check_kernels.py
```

## Scripts

```sh
uv run --group dev python examples/make_quickstart.py   # rebuild and run the quickstart notebook
uv run --group dev python examples/make_figures.py      # redraw the README's figures
```

The quickstart notebook is generated by `examples/make_quickstart.py`: edit the script and rerun it rather
than editing the notebook; a test fails if they differ. The scripts behind [BENCHMARKS](BENCHMARKS.md) are
in `benchmarks/`, run from there with `uv run --group bench python <script>`; its
[README](benchmarks/README.md) groups them by purpose.

## Releases

The version is set in one place, `crates/siann-py/Cargo.toml`, which maturin also uses for the Python
package. Before a release, run the tests and `check_kernels.py` on a Mac with Apple silicon, where the GPU
tests run. Then commit the new version, push, and create a release on GitHub whose tag is `v` followed by
the version (for example `v0.1.0`). The release workflow (`.github/workflows/release.yml`) checks that the
tag matches the version, runs CI, builds a wheel (a built package, so that users need no Rust compiler)
for each platform:

| Platform | Wheel |
| --- | --- |
| Linux, x86-64 and ARM | manylinux: glibc-based distributions (most; not Alpine); x86-64 needs AVX2 |
| macOS, Apple silicon | macOS 11 or later; installs MLX, the GPU backend |
| Windows, x86-64 | needs AVX2 |

The x86-64 wheels are compiled for x86-64-v3, which requires AVX2 and FMA (Intel processors from Haswell,
2013, and AMD's from Excavator, 2015): that makes L1 and L-infinity search 1.5-2.4x faster than a build for
any x86-64 processor (BENCHMARKS, [On Linux](BENCHMARKS.md#on-linux)). On an older processor, `import
siann` raises an ImportError saying so (`siann._build`, checked before the Rust extension loads), and
`pip install --no-binary siann siann` builds siann for that machine from the source distribution.

and a source distribution, and smoke-tests each (`scripts/smoke_test.py`: exact search by every metric
against NumPy, an IVF reaching its recall target, a save and load) on its own platform on Python 3.12
and 3.14. The wheels are abi3, built against Python's stable interface, so one wheel per platform serves
every Python from 3.12 on. The workflow then publishes to PyPI through trusted publishing: PyPI accepts
packages from this workflow without a stored token.

To rehearse, run the workflow by hand (Actions, Release, Run workflow): it does the same, but publishes to
TestPyPI, with the version `VERSION.devN`, N the run number, since an index accepts each version only once.

## Rules for changing the code

**Results.**

- **Exact search is the oracle.** Every kernel and index is checked against NumPy's exact search
  (`check_kernels.py`). A change that should not move results is checked bit for bit against outputs
  saved before the change, on fixed seeds; a change that does move them says why.
- **A new default must be no slower than the old one on any measured case,** single queries, batches of
  100 and batches of 10,000 alike.
- **Every number in the docs comes from a committed script,** with its raw output in
  `benchmarks/results/` and its place in [BENCHMARKS](BENCHMARKS.md). An idea that does not pay goes into
  IMPLEMENTATION's [What does not pay](IMPLEMENTATION.md#what-does-not-pay), with its numbers.

**Timing.**

- **Time each path by itself, warmed up.** A GPU call right after CPU calls runs up to 40% slower, and a
  fresh index's first GPU calls are slower than later ones, so timings taken in alternation, or cold,
  favor the CPU.

**GPU kernels.**

- **Write each kernel once,** in `siann._metal`: MLX and PyTorch compile the same text, so the two GPU
  backends cannot drift apart.
- **Pass sizes such as the batch size at run time, not as compile-time constants.** Compiled in, every
  new batch size recompiles the kernel, 26-74 ms on top of a 1-4 ms search. Compile in only what sizes an
  array in registers or threadgroup memory (k, threads per query) or a loop worth unrolling (the
  dimension).

**Rust.**

- **Safe Rust only.** siann's code has no `unsafe` (code the compiler cannot check for memory safety),
  and every case so far has a safe alternative: NumPy for BLAS calls, a comparison and select for a
  maximum, a buffer for float16, plain loops over contiguous bytes for integer arithmetic. Calling
  Accelerate from Rust would be `unsafe`, so NumPy makes the call and Rust ranks the products, reading
  NumPy's arrays in place through rust-numpy (the PyO3 project's NumPy bindings).
- **Check the assembly, not just the timing.** The compiler turns plain loops into NEON instructions
  (Apple's vector instructions), and its choice of which loop to vectorize decides the speed. That choice
  is easy to see in the emitted instructions (`fabd.4s`, `udot`) and easy to miss in a timing alone.
- **Choose the layout for the arithmetic.** Floating-point sums may not be reordered, so the blocked
  layout (8 vectors per block, dimension by dimension) gives one running distance per lane. Integer sums
  may be reordered, so the integer path reads each vector's bytes contiguously.
- **Write a floating-point maximum as a comparison and select, loop over flat slices, and give one
  query's parallel work a thread pool of its own:** `f32::max`, nested arrays and rayon's global pool
  each cost speed, measured in [What does not pay](IMPLEMENTATION.md#what-does-not-pay).
